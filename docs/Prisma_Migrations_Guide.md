# ReserveHub — Prisma 7 Migration Workflow and Database Change Policy

**Repository:** `ishara-dhanushan/Reserve-Hub`  
**Date:** 13 October 2026  
**Compatible baseline:** Prisma ORM **7.x** (do not mix v6/v8 flags)

## 1. Philosophy — reliable, reviewable migrations

ReserveHub is a **new, small database**: prefer Prisma's native migration engine with versioned SQL, keeping every migration reviewable and reproducible. Adopt a custom 443-only runner **only if direct access really fails**, and test its migration bookkeeping before relying on it.

**Source of truth:** committed `prisma/schema.prisma` plus `prisma/migrations/**/migration.sql` and the database's `_prisma_migrations` history—not a raw snapshot alone.

## 2. Ownership of files

```text
prisma/
├── schema.prisma                  # desired declarative schema
├── migrations/
│   ├── migration_lock.toml        # generated by Prisma
│   ├── 20261013xxxxxx_init_reservehub/
│   │   └── migration.sql          # initial tables, enum types, FKs, indexes
│   └── 20261014xxxxxx_prevent_booking_overlap/
│       └── migration.sql          # reviewed PostgreSQL custom constraints
└── seed.ts                        # optional demo data

prisma.config.ts                    # CLI datasource, migration path, seed command
src/lib/prisma.ts                   # runtime adapter (not CLI)
```

The timestamps above are **illustrative placeholders**, not claimed created migrations. Do not hand-create a migration folder claiming Prisma applied it unless its history is reconciled correctly.

## 3. Standard development migration flow (recommended)

### A. Before making a schema change

1. Switch to the issue's feature branch; pull latest `main`.
2. Confirm the Neon **development** branch/DB and local `.env` values.
3. Check the current migration state:

```bash
npm run prisma:migrate:status
npm run prisma:validate
```

4. Inspect any drift warnings before modifying tables.

### B. Create, review, and then apply a change

1. Edit `prisma/schema.prisma` in a focused way.
2. Validate the schema and check for pre-existing pending migrations:

```bash
npm run prisma:validate
npm run prisma:migrate:status
```

3. Generate the new migration file **without applying it**:

```bash
npm run prisma:migrate:dev -- --name add_descriptive_change --create-only
```

4. Open `prisma/migrations/<timestamp>_add_descriptive_change/migration.sql` and inspect all generated statements for unintended drops, type conversions, data loss, or missing constraints. Edit the SQL before applying it if necessary. **Stop** if the migration does not match the intended change.
5. When the generated SQL **and any other pending migrations** have been reviewed, confirm that `DIRECT_URL` targets the intended database and apply the pending SQL migration files:

```bash
npm run prisma:migrate:deploy
```

6. Regenerate Prisma Client, verify the migration status, and run tests:

```bash
npm run prisma:generate
npm run prisma:migrate:status
npm run lint
npm run build
```

7. Commit `schema.prisma`, `prisma.config.ts` (if changed), and all intended `prisma/migrations/` SQL. **Never** commit secrets or generated .env credentials.

**Important:** `--create-only` prevents the _new_ migration from being applied before review. `migrate deploy` applies **all pending migrations**, not just the one you created; do not deploy if another pending migration is unreviewed. `migrate deploy` does not detect schema drift and requires separately verifying the schema/migration history. `migrate dev --create-only` still uses the development migration engine and a shadow database; stop if it suggests a database reset.

### C. When custom SQL is needed (GiST exclusion constraint)

PostgreSQL needs an exclusion constraint to reliably prevent two concurrent `CONFIRMED` reservations for the same resource. A simple Prisma model cannot express it.

1. Finish the initial schema migration first.
2. Create the next migration **without applying it yet**:

```bash
npm run prisma:migrate:dev -- --name prevent_booking_overlap --create-only
```

3. Open the newly created `prisma/migrations/<timestamp>_prevent_booking_overlap/migration.sql`. Append/review:

```sql
-- B-tree equality operators for GiST, used with the resourceId text/UUID.
CREATE EXTENSION IF NOT EXISTS btree_gist;

-- Half-open ranges allow adjacent reservations (09:00–10:00, 10:00–11:00).
-- PostgreSQL raises SQLSTATE 23P01 for excluded overlapping inserts.
ALTER TABLE "Reservation"
ADD CONSTRAINT "reservation_no_confirmed_overlap"
EXCLUDE USING gist (
  "resourceId" WITH =,
  tstzrange("startAt", "endAt", '[)') WITH &&
)
WHERE ("status" = 'CONFIRMED');

-- A booking must end after it starts.
ALTER TABLE "Reservation"
ADD CONSTRAINT "reservation_valid_interval"
CHECK ("endAt" > "startAt");
```

4. **Verify actual table/column/enum SQL names** from the initial migration and the Prisma schema before executing; adjust if renamed. Make sure Neon allows `btree_gist` for this project.
5. After reviewing and saving the SQL (including any other pending migrations), apply it and verify:

```bash
npm run prisma:migrate:deploy
npm run prisma:generate
npm run prisma:migrate:status
```

6. Write an integration test that submits two overlapping reservations concurrently and verifies **one succeeds and one receives a conflict**. App-level checks remain useful for friendly errors but do not replace the database constraint.

**Do not run `migrate dev` against a production database.** It uses a shadow database for drift detection and is intended for development.

### D. Production/test deploy only after review

For a separate deployment database, after committing migrations and verifying the target URL:

```bash
npm run prisma:migrate:status
npm run prisma:migrate:deploy
npm run prisma:generate
```

Use `prisma migrate deploy` rather than `migrate dev` for deployed environments; do not assume that `migrate deploy` proves there is no drift. Review schema/SQL and run functional verification independently. An assessment submission requires that another developer can reproduce the schema from versioned migrations.

## 3.1 Shadow database troubleshooting for Neon

`prisma migrate dev` uses a temporary **shadow database** to detect drift. If your Neon role cannot create databases, Prisma may fail even when `DIRECT_URL` is valid. In that case, create a **separate disposable shadow database** (or other compatible isolated database) and configure `SHADOW_DATABASE_URL` in `.env`:

```dotenv
# Must be a DIFFERENT database from DIRECT_URL and safe for Prisma to reset.
SHADOW_DATABASE_URL="postgresql://USER:PASSWORD@SHADOW-ENDPOINT.REGION.aws.neon.tech/SHADOW_DB?sslmode=require"
```

Then update the `datasource` entry of `prisma.config.ts`:

```ts
  datasource: {
    // Development and migration target database.
    url: env("DIRECT_URL"),
    // Disposable isolated database for Prisma's drift-detection replay.
    shadowDatabaseUrl: env("SHADOW_DATABASE_URL"),
  },
```

**Critical:** Never set `SHADOW_DATABASE_URL` to the same database as `DIRECT_URL`. Prisma resets an explicitly configured shadow database while running development migrations. If you haven't created a dedicated shadow database, **do not add this property yet**. For Prisma 7, these URLs belong in `prisma.config.ts`, not in the `datasource` block of `schema.prisma`. See <https://www.prisma.io/docs/orm/v7/prisma-migrate/understanding-prisma-migrate/shadow-database>.

## 4. Schema drift and history validation

| Check                              | Command                                                                                         | Purpose                                                            |
| ---------------------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Syntax/relations                   | `npm run prisma:validate`                                                                       | Catch schema errors before DB writes                               |
| Migration history                  | `npm run prisma:migrate:status`                                                                 | Detect pending/failed migrations in target DB                      |
| Live DB vs desired Prisma schema   | `npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --exit-code` | Exit code 0 = no supported differences; 2 = differences; 1 = error |
| Generate executable SQL for review | `npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script`    | **Read only**; output alone does not apply                         |

Prisma `migrate diff` does **not** detect all unsupported PostgreSQL features (such as all custom constraints/extensions). In particular, manually inspect the exclusion constraint as part of your test/deployment verification. Never interpret a zero diff as proof that all custom SQL is present.

**If the migration history differs from the database:** stop; compare committed migration files, `_prisma_migrations`, and the actual Neon schema. Do not delete migrations, manually clear the table, or run `migrate reset` on a shared database.

## 5. Branch and PR rules

- `main` is the stable demonstration branch. Feature work uses `feature/rh-XX-short-topic` names corresponding to the issue identifiers in `docs/IMPLEMENTATION_TICKETS.md`.
- For each schema change, include the Prisma model diff, the SQL migration, a note about compatibility/data integrity, and verification output in the PR.
- Merge schema tickets before API tickets that depend on generated fields.
- Do not rewrite/delete a migration that has already been applied to a shared DB; add a corrective migration instead.
- Never put secrets, Neon connection strings, or password hashes in PR descriptions/screenshots.
- Keep tests and migration operations against development or isolated test databases; confirm database identity before destructive operations.

Suggested PR checklist:

```markdown
- [ ] Prisma schema matches finalized requirements/ER diagram
- [ ] Migration SQL generated using `--create-only` and reviewed before `prisma:migrate:deploy`
- [ ] Migration SQL reviewed for safety and unsupported PostgreSQL features
- [ ] `npm run prisma:validate` passed
- [ ] `npm run prisma:migrate:status` reviewed for the intended database
- [ ] Prisma Client regenerated
- [ ] Feature tests and `npm run build` passed
- [ ] No credentials or temporary migration files committed
```

## 6. Restricted-network fallback (only if direct TCP is actually blocked)

**What we know:** Some networks block direct PostgreSQL access on port 5432 while HTTPS/WebSocket connections on port 443 remain available. **This does not automatically mean ReserveHub needs a custom workaround.**

### First response (strongly preferred)

1. Verify direct URL and credentials.
2. Try an authorized network that allows the Prisma CLI to connect to Neon's PostgreSQL endpoint.
3. Run the standard `migrate dev` or `migrate deploy` process and preserve the generated SQL migrations.
4. Use Neon's serverless driver for application runtime traffic when direct TCP is unavailable.

### Only if no usable direct connection is available

Do **not** jump straight to `npx prisma db push`: it bypasses migration history and may not support your custom GiST SQL. A custom fallback is a separately tested engineering task, not a one-line replacement for Prisma Migrate.

The fallback _design_ would require:

```text
schema.prisma (desired)  +  schema.applied.prisma (last *verified* state)
                │
                v
prisma migrate diff --from-schema ... --to-schema ... --script
                │
                v
REVIEWED, VERSIONED SQL MIGRATION
                │
                v
NEON serverless SQL transport on port 443 (explicit transaction where supported)
                │
                v
verify actual database shape + reconcile _prisma_migrations correctly
                │
                v
update schema.applied.prisma only after all verification passes
```

Important safeguards:

- Prisma 7 supports `--from-schema` and `--to-schema` as illustrated; old `--from-url` / `--to-url` / `--from-schema-datasource` flags are **removed**.
- Keep custom PostgreSQL SQL (GiST constraint, extension) in the versioned reviewed migration rather than relying on Prisma's schema diff to generate it.
- A manually executed SQL file **does not automatically appear in** `_prisma_migrations`. Without accurate reconciliation, later `migrate deploy` can reapply SQL or fail. `npx prisma migrate resolve --applied <migration_name>` is valid only when the target database actually matches that migration, and itself needs a working Prisma database connection.
- An HTTP/WS runner must be separately designed for transactional DDL behavior, idempotency policy, checksum records, partial failures, and concurrency of migration runs. Do **not** directly insert arbitrary records into `_prisma_migrations` based on guesses.
- The Neon SQL Editor can execute reviewed SQL for one-off investigation, but avoid treating manual SQL plus an outdated migration ledger as a reproducible project setup.
- If the custom fallback is necessary, pause work and validate it against a disposable Neon test branch before touching the assessment DB; record exact commands and proof in the relevant issue.

### What not to do

- Do not run `migrate reset` against shared/prod data.
- Do not run `db push` on the submission database to “fix” a migration conflict.
- Do not edit a previously applied migration's SQL and pretend history remains the same.
- Do not mark a migration as applied before its SQL has **actually** taken effect.
- Do not use the local Prisma runtime adapter as proof the Prisma CLI migrations will work over HTTPS.

## 7. Windows PowerShell and Linux Bash commands

All `npm`, `npx`, and Git commands in this guide have identical syntax on both systems. The following operations differ by shell.

**Create the migrations directory only when it does not exist:**

PowerShell:

```powershell
New-Item -ItemType Directory -Force prisma/migrations
```

Linux Bash:

```bash
mkdir -p prisma/migrations
```

**Save generated diff output to a file:**

PowerShell:

```powershell
npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script --output migration-review.sql
```

Linux Bash:

```bash
npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script --output migration-review.sql
```

For both shells, `--output` is safer than output redirection when preserving SQL text encoding. **Generating this review SQL does not mark or apply a migration.**

## 8. Definition of Done

- [ ] Fresh database can be created from committed migration history.
- [ ] Existing database migrates without dropping historical reservations.
- [ ] Migration SQL is generated with `--create-only`, reviewed, then applied using `npm run prisma:migrate:deploy`.
- [ ] Migration history is committed and corresponds to the actual DB state.
- [ ] Custom PostgreSQL exclusion constraint is present and tested.
- [ ] `npm run prisma:migrate:status` reports expected status on the intended DB.
- [ ] Schema drift check does not report unintended Prisma-managed differences.
- [ ] A second reviewer can follow the Neon setup guide without private credentials.
